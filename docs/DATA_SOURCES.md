# Data sources and provenance

Status words used below: **live** (the current ingestion retrieved and validated upstream data), **cached** (the API serves valid NASA observations stored by an earlier retrieval), **demo** (synthetic values generated by software), **unavailable** (no usable observations), and **Assumption** (typed in by the team, not yet verified).

## NASA POWER (climate)

| Item | Value |
|---|---|
| Service | NASA POWER (Prediction Of Worldwide Energy Resources), daily "point" API |
| URL | `https://power.larc.nasa.gov/api/temporal/daily/point` |
| Community | `AG` (agronomy) |
| Parameters | `PRECTOTCORR` (corrected precipitation, mm/day), `T2M_MAX` and `T2M_MIN` (daily max / min air temperature at 2 m, deg C) |
| Period requested | 2001-01-01 to the end of last year (default), configurable with `--start` and `--end` years |
| Access | No key needed |
| Spatial resolution | Meteorology on a grid of roughly 0.5 degrees (tens of km). Values describe a grid cell, **not a farm** |
| Missing values | NASA marks them with a fill value (-999). The parser reads the fill value from the response and stores `null` |

What is stored per retrieval (`DatasetRun`): endpoint, request parameters, retrieval timestamp, product title and sources from NASA's response header, fill value, units, row count, missing count and any warnings. Daily rows retain the legacy POWER fields and a `measurements` object for source-specific values. The API returns this as `climate.provenance`, and the interface shows it under "Climate evidence". Stored real observations are reported as `dataStatus: "cached"`; a successful command is not retroactively called `live`.

Checks applied before storing: coordinates and dates are validated, required parameters and matching date sets are present, units are mm and Celsius, fill values become `null`, values outside plausible limits become missing, and a district is refused if any variable is missing on more than 20% of days. Failures are recorded as `FAILED` runs and shown at `/api/health/data`; successful replacement does not delete failure history.

**Verification status.** A live three-day request to the official endpoint was verified on 2026-11-02 for Rajshahi coordinates and returned the expected variables and units. Persistence against a real database and a full historical ingestion remain environment-dependent; fixture tests do not prove those paths.

## Grid cells (field-level association)

`ClimateGridCell` records one cell of a provider's grid, and `DatasetRun.gridCellId` says which cell a run
describes. `src/geo/climateGrid.js` computes the cell for any point.

**Grid (verified 2026-11-04):** the POWER meteorology grid is 0.5 degrees of latitude by 0.625 degrees of longitude with cell
centres at latitude `k * 0.5` and longitude `-180 + j * 0.625`. POWER echoes back the coordinates you ask for, so they cannot
identify the cell; the **data** are the evidence. Two checks agreed with the grid:

- `npm run check:grid-consistency` (offline, read-only): the 12 stored district series group exactly as the cells predict
  (Jashore and Khulna share a cell and have identical data; every other district differs).
- `npm run check:power-grid` (live NASA, a few minutes): walking points 0.05 degrees apart, the returned temperatures change
  within one step of every expected edge (latitude 24.25 and 24.75, longitude 88.4375 and 89.0625), with no unexpected edge.

Limits of that verification: edge positions are known to about 0.025 degrees (the sampling step), and the live probe covered
the Rajshahi area; the rest of the country is covered only by the 12-district consistency check. Re-run both checks if the
constants in `src/geo/climateGrid.js` change. `POWER_GRID.verified` controls whether responses warn that the grid is unconfirmed.

Existing runs get their cell with `npm run db:backfill-cells` (add `-- --dry-run` to preview). New ingestions record
it automatically. A run is placed in the cell containing its district's reference point, so a district run serves
every field in that cell and no other cell. Cells without a run are reported as `CLIMATE_CELL_NOT_INGESTED`; ingesting
arbitrary cells is the next milestone.

## Ingestion commands and operations

Historical ingestion:

```bash
npm run ingest:nasa -- --district=rajshahi --start=2001 --end=2025
```

The command is repeatable and records each failed attempt. Successful runs retain only
the latest successful dataset for the same district/source/type, while failed run history
is preserved. Requests are serialized per district/date range using the
`DatasetIngestionLock` table; stale locks older than 30 minutes can be recovered.

Incremental refresh:

```bash
npm run ingest:refresh -- --lag=7 --overlap=2
```

Refresh starts a small configurable overlap before the last stored observation, ends at
the configured lag behind today, and preserves previously valid non-null values when a
re-fetched response contains a missing value. It never fabricates current observations.
See docs/LIVE_DATA_PRODUCTION.md for the ready-made daily GitHub Actions schedule.
Run this command from a separate scheduled worker or platform cron job, not from the
Express web process.

## Synthetic demo data

`npm run db:seed:synthetic` creates deterministic, software-generated daily values (mulberry32 random numbers, seeded from the district name) with **no trend by construction**. It exists only so the screens can be demonstrated offline. It is stored with `isSynthetic = true`, a loud notice appears in the API and UI, and real NASA data always takes priority. Never quote a number from synthetic data as a finding.

## Districts (Assumption)

Twelve pilot districts, not all 64. Coordinates are approximate district-headquarters positions typed from general knowledge, not from an official gazetteer. They only select a NASA grid cell, which is far coarser than the error, but they must be verified before any stronger claim. Neighbouring districts can fall in the same grid cell and then share identical climate values.

## Crop traits (Assumption)

Typical months in the field, seasonal water need range, heat threshold, heat sensitivity, salinity tolerance, waterlogging tolerance and input intensity for 22 crops (rice, wheat, mustard, potato, pulses, maize, jute, vegetables, oilseeds and sweet potato). They come from general agronomic knowledge, are stored with `basis = UNVERIFIED_GENERAL_KNOWLEDGE`, and are shown that way next to every result. The expanded list covers common crops grown across Bangladesh's aman, rabi, pre-monsoon and monsoon periods; it does not mean every crop can be grown continuously in every location.

**Action before submission:** an agronomist or the team must check each value against BRRI, BARI and BARC publications and FAO Irrigation and Drainage Paper 56, record the citation per value, and only then change `basis`.

## Soil

No soil dataset is used. Soil enters only as what the user selects (salinity and drainage), matched against crop tolerance levels. This is a stated limitation in the app.

## Future dataset integration

NASA GPM IMERG is the planned second source, for satellite precipitation. It is not integrated yet. POWER and IMERG differ in spatial resolution, time coverage and measurement method, so they must be stored as separate sources with their own units and resolution notes and never merged into one series. SMAP, HLS and Sentinel-1 are explicitly out of scope.

## Not used

Soil-moisture and vegetation products, satellite vegetation indices (such as NDVI), market prices, pests, diseases, labour, seed supply and flood timing are not modelled.
